# psbAI

RAG-ассистент по нормативной базе ООО «ПСБ»: законы и внутренние документы компании (регламенты, договоры, дополнительные соглашения). Отвечает на вопросы строго по содержимому базы знаний, со ссылками на статьи и пункты.

## Как это работает

```
knowledge-base.zip ──► chunk.py ──► index/kb.db ──► embed.py ──► search_table.py ──► generate.py
   (документы)        нарезка      (SQLite)      эмбеддинги    гибридный поиск    ответ LLM
```

1. **Чанкинг** (`chunk.py`) — документы режутся на фрагменты с сохранением юридической структуры.
2. **Эмбеддинги** (`embed.py`) — для каждого чанка считается dense-вектор (`BAAI/bge-m3`, 1024) и список токенов для BM25.
3. **Поиск** (`search_table.py`) — Dense (cosine) + Sparse (BM25) → слияние через RRF → штраф для утративших силу документов → дедупликация → реранкер.
4. **Генерация** (`generate.py`) — найденные чанки подставляются в промпт, LLM отвечает только по контексту.
5. **Точка входа** (`solution.py`) — для платформы: готовит индекс, параллельно отвечает на все вопросы в рамках бюджета времени и всегда записывает полный `submission.csv`.

## Структура проекта

| Файл | Назначение |
|---|---|
| `chunk.py` | Чтение файлов, нарезка на чанки, извлечение метаданных, сохранение в `index/kb.db` |
| `embed.py` | Расчёт эмбеддингов с retry, возобновлением и параллельными батчами |
| `search_table.py` | Загрузка индекса в память, гибридный поиск, реранкинг |
| `generate.py` | Системный промпт, сборка контекста, вызов LLM, CLI |
| `solution.py` | Пакетная обработка `questions.csv` → `submission.csv` |
| `requirements.txt` | Зависимости |

## Конфигурация

Все параметры задаются переменными окружения.

**Обязательные**

| Переменная | Описание |
|---|---|
| `LLM_BASE_URL` | Базовый URL OpenAI-совместимого API |
| `LLM_API_KEY` | Ключ API |

**Опциональные**

| Переменная | По умолчанию | Описание |
|---|---|---|
| `DATA_DIR` | `data` | Папка с данными (`knowledge-base.zip`, `questions.csv`) |
| `EMB_MODEL` | `BAAI/bge-m3` | Модель эмбеддингов (размерность 1024) |
| `RERANKER_MODEL` | `Qwen3-Reranker-8B` | Модель реранкера (эндпоинт `/rerank`) |
| `RERANKER_TOP_N` | `TOP_K` | Сколько чанков оставить после реранка |
| `LLM_MODEL` / `OPENAI_MODEL` / `GEN_MODEL` | `gpt-4o-mini` | Модель генерации (берётся первая заданная) |
| `TOP_K` | `8` | Сколько чанков отдавать в контекст |
| `TEMPERATURE` | `0.2` | Температура генерации |
| `MAX_TOKENS` | `1024` | Лимит токенов ответа |
| `MAX_WORKERS` | `4` в `embed.py`, `8` в `solution.py` | Число параллельных потоков |
| `TIME_BUDGET_SEC` | `1020` (17 мин) | Мягкий бюджет: после него новые вопросы не стартуют |
| `HARD_EXTRA_SEC` | `90` | Дополнительное время до принудительной записи результата |

## Использование

### Полный пайплайн для платформы

```bash
export LLM_BASE_URL=... LLM_API_KEY=...
export DATA_DIR=data
python solution.py
```

Ожидает `data/knowledge-base.zip` и `data/questions.csv` (колонки `id`, `question`). На выходе — `submission.csv` с колонками `id,answer`.

### По шагам

```bash
# 1. Нарезка в index/kb.db (--inspect — только статистика и примеры, без записи)
python chunk.py
python chunk.py --inspect --show 5

# 2. Эмбеддинги (по умолчанию считаются только чанки без вектора; --force — пересчитать все)
python embed.py
python embed.py --force

# 3. Проверка поиска
python search_table.py "срок оплаты по договору" --k 5 --rerank

# 4. Ответ на вопрос (--show-context печатает найденные чанки, --no-rerank отключает реранкер)
python generate.py "Какой срок рассмотрения претензии?" --show-context
```

## Подробности реализации

### Чанкинг

Тип документа определяется по префиксу имени файла: `законы…` → закон, `документы…` → документ компании.

- **Законы** — статья режется по частям (`1.`, `2)`, `п. 3`, `подпункт 4`), части склеиваются до 3500 символов. Короткие статьи остаются одним чанком.
- **Документы компании** — разбивка по разделам (`1. Общие положения`, `Статья`, `Глава`, `Приложение`…), внутри — по пунктам (`2.3`, `4.1.2`), группы до 1800 символов.
- Слишком длинные фрагменты режутся по абзацам → предложениям → словам с перекрытием 150 символов; гарантируется, что чанк не превышает лимит.
- **Метаданные**: номер и дата документа, признак «утратил силу», признак дополнительного соглашения и номер основного договора (`amends_doc`).

Поддерживаемые форматы: `.txt`, `.md`, `.json`, `.csv`, `.docx` (включая таблицы), `.pdf`, `.html`/`.htm`.

### Хранилище

SQLite `index/kb.db`, таблица `chunks`: `id`, `type`, `file`, `doc`, `section`, `clause`, `doc_date`, `is_amendment`, `lost`, `amends_doc`, `part`, `context`, `text`, `dense_vec` (JSON), `sparse_tokens`.

### Эмбеддинги

- Текст для эмбеддинга: `документ | раздел | ч.N | контекст | п.X` + текст чанка.
- Батчи по 16, до 5 попыток с экспоненциальной задержкой, проверка размерности.
- Результаты коммитятся по мере готовности — прерванный запуск можно продолжить, повторно запустив `embed.py`.
- Чанки, чей батч не удался, остаются без вектора и ищутся только через BM25.

### Поиск

- Индекс загружается один раз за процесс (потокобезопасно): векторы — нормализованная numpy-матрица, BM25 — предрассчитанные вклады термов.
- Токенизация — по буквам/цифрам с усечением слов до 6 символов (грубый стемминг для русского).
- Слияние dense и sparse через RRF (`k=60`).
- Утратившие силу документы получают множитель `0.3`.
- Из кандидатов (`3 × k`) убираются дубли внутри одного файла (пересечение токенов > 70 %).
- Реранкер вызывается через `/rerank`; если он недоступен, возвращается порядок после RRF.

### Генерация

Системный промпт требует отвечать только по контексту, ссылаться на статьи и пункты, помечать утратившие силу документы и дополнительные соглашения (с указанием основного договора). Если контекст пуст или релевантность слишком низка — возвращается «В предоставленной базе знаний информация отсутствует». При ошибках API — до 3 попыток.

### Устойчивость `solution.py`

- Любая ошибка индексации или вопроса не мешает записать `submission.csv` со всеми `id`.
- Вопросы, не уложившиеся в бюджет времени, получают запасной ответ.
- Ответ обрезается до 10 000 символов.
