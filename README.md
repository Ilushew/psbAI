# psbAI

## Запуск проекта

### Требования

Для запуска необходимы:
- Docker Engine
- Docker Compose (плагин `docker compose`)
- API-ключ OpenAI-совместимого LLM API

### 1. Клонирование репозитория

```bash
git clone https://github.com/Ilushew/psbAI.git
cd psbAI
```

### 2. Настройка окружения

Создайте файл `.env` на основе примера:

```bash
cp .env.example .env
```

Добавьте в `.env` параметры подключения к LLM API:

```env
LLM_BASE_URL=https://your-api-provider/v1
LLM_API_KEY=your-api-key
LLM_MODEL=gpt-4o-mini
```

- `LLM_BASE_URL` — адрес OpenAI-совместимого API.
- `LLM_API_KEY` — ключ доступа к API.
- `LLM_MODEL` — модель для генерации ответов.

API-провайдер должен поддерживать генерацию текста и создание эмбеддингов с использованием модели `BAAI/bge-m3` (размерность вектора — 1024). Для работы реранкера также желательно наличие совместимого endpoint `/rerank`; при его недоступности используется поиск без реранкинга.

### 3. Подготовка базы знаний

Поместите исходные документы в директорию `data/`.

Поддерживаемые форматы: `.txt`, `.md`, `.json`, `.csv`, `.docx`, `.pdf`, `.html`.

Если документы предоставлены архивом `knowledge-base.zip`, предварительно распакуйте его:

```bash
unzip data/knowledge-base.zip -d data/knowledge-base
```

### 4. Построение поискового индекса

Создайте директорию для индекса:

```bash
mkdir -p index
```

Соберите Docker-образ AI Service:

```bash
docker compose build ai-service
```

Выполните нарезку документов на фрагменты:

```bash
docker compose run --rm ai-service python chunk.py
```

Создайте эмбеддинги для полученных фрагментов:

```bash
docker compose run --rm ai-service python embed.py
```

В результате будет создан индекс `index/kb.db`, используемый для поиска по базе знаний.

### 5. Запуск приложения

Запустите все сервисы:

```bash
docker compose up --build -d
```

Docker Compose автоматически запустит:
- **PostgreSQL** — хранение пользовательских сессий, чатов и сообщений.
- **AI Service** — поиск по базе знаний и генерация ответов.
- **Go Backend** — HTTP API и веб-интерфейс.

### 6. Проверка работы

Проверьте состояние контейнеров:

```bash
docker compose ps
```

Проверьте доступность Backend:

```bash
curl http://localhost:8080/health
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

RAG-ассистент по нормативной базе ООО «ПСБ»: законы и внутренние документы компании (регламенты, договоры, дополнительные соглашения). Отвечает на вопросы строго по содержимому базы знаний, со ссылками на статьи и пункты.

## Как это работает

```
knowledge-base.zip ──► chunk.py ──► index/kb.db ──► embed.py ──► search_table.py ──► generate.py
   (документы)        нарезка      (SQLite)      эмбеддинги    гибридный поиск    ответ LLM
```

1. **Чанкинг** (`chunk.py`) — документы режутся на фрагменты с сохранением юридической структуры.
2. **Эмбеддинги** (`embed.py`) — для каждого чанка считается dense-вектор (`BAAI/bge-m3`, 1024) и список токенов для BM25.
3. **Поиск** (`search_table.py`) — Dense (cosine) + Sparse (BM25) → слияние через RRF → штраф для утративших силу документов → дедупликация → реранкер.
4. **Генерация** (`generate.py`) — найденные чанки подставляются в промпт, LLM отвечает только по контексту.
5. **Точка входа** (`solution.py`) — для платформы: готовит индекс, параллельно отвечает на все вопросы в рамках бюджета времени и всегда записывает полный `submission.csv`.

## Структура проекта

| Файл | Назначение |
|---|---|
| `chunk.py` | Чтение файлов, нарезка на чанки, извлечение метаданных, сохранение в `index/kb.db` |
| `embed.py` | Расчёт эмбеддингов с retry, возобновлением и параллельными батчами |
| `search_table.py` | Загрузка индекса в память, гибридный поиск, реранкинг |
| `generate.py` | Системный промпт, сборка контекста, вызов LLM, CLI |
| `solution.py` | Пакетная обработка `questions.csv` → `submission.csv` |
| `requirements.txt` | Зависимости |

## Конфигурация

Все параметры задаются переменными окружения.

**Обязательные**

| Переменная | Описание |
|---|---|
| `LLM_BASE_URL` | Базовый URL OpenAI-совместимого API |
| `LLM_API_KEY` | Ключ API |

**Опциональные**

| Переменная | По умолчанию | Описание |
|---|---|---|
| `DATA_DIR` | `data` | Папка с данными (`knowledge-base.zip`, `questions.csv`) |
| `EMB_MODEL` | `BAAI/bge-m3` | Модель эмбеддингов (размерность 1024) |
| `RERANKER_MODEL` | `Qwen3-Reranker-8B` | Модель реранкера (эндпоинт `/rerank`) |
| `RERANKER_TOP_N` | `TOP_K` | Сколько чанков оставить после реранка |
| `LLM_MODEL` / `OPENAI_MODEL` / `GEN_MODEL` | `gpt-4o-mini` | Модель генерации (берётся первая заданная) |
| `TOP_K` | `8` | Сколько чанков отдавать в контекст |
| `TEMPERATURE` | `0.2` | Температура генерации |
| `MAX_TOKENS` | `1024` | Лимит токенов ответа |
| `MAX_WORKERS` | `4` в `embed.py`, `8` в `solution.py` | Число параллельных потоков |
| `TIME_BUDGET_SEC` | `1020` (17 мин) | Мягкий бюджет: после него новые вопросы не стартуют |
| `HARD_EXTRA_SEC` | `90` | Дополнительное время до принудительной записи результата |

## Использование

### Полный пайплайн для платформы

```bash
export LLM_BASE_URL=... LLM_API_KEY=...
export DATA_DIR=data
python solution.py
```

Ожидает `data/knowledge-base.zip` и `data/questions.csv` (колонки `id`, `question`). На выходе — `submission.csv` с колонками `id,answer`.

### По шагам

```bash
# 1. Нарезка в index/kb.db (--inspect — только статистика и примеры, без записи)
python chunk.py
python chunk.py --inspect --show 5

# 2. Эмбеддинги (по умолчанию считаются только чанки без вектора; --force — пересчитать все)
python embed.py
python embed.py --force

# 3. Проверка поиска
python search_table.py "срок оплаты по договору" --k 5 --rerank

# 4. Ответ на вопрос (--show-context печатает найденные чанки, --no-rerank отключает реранкер)
python generate.py "Какой срок рассмотрения претензии?" --show-context
```

## Подробности реализации

### Чанкинг

Тип документа определяется по префиксу имени файла: `законы…` → закон, `документы…` → документ компании.

- **Законы** — статья режется по частям (`1.`, `2)`, `п. 3`, `подпункт 4`), части склеиваются до 3500 символов. Короткие статьи остаются одним чанком.
- **Документы компании** — разбивка по разделам (`1. Общие положения`, `Статья`, `Глава`, `Приложение`…), внутри — по пунктам (`2.3`, `4.1.2`), группы до 1800 символов.
- Слишком длинные фрагменты режутся по абзацам → предложениям → словам с перекрытием 150 символов; гарантируется, что чанк не превышает лимит.
- **Метаданные**: номер и дата документа, признак «утратил силу», признак дополнительного соглашения и номер основного договора (`amends_doc`).

Поддерживаемые форматы: `.txt`, `.md`, `.json`, `.csv`, `.docx` (включая таблицы), `.pdf`, `.html`/`.htm`.

### Хранилище

SQLite `index/kb.db`, таблица `chunks`: `id`, `type`, `file`, `doc`, `section`, `clause`, `doc_date`, `is_amendment`, `lost`, `amends_doc`, `part`, `context`, `text`, `dense_vec` (JSON), `sparse_tokens`.

### Эмбеддинги

- Текст для эмбеддинга: `документ | раздел | ч.N | контекст | п.X` + текст чанка.
- Батчи по 16, до 5 попыток с экспоненциальной задержкой, проверка размерности.
- Результаты коммитятся по мере готовности — прерванный запуск можно продолжить, повторно запустив `embed.py`.
- Чанки, чей батч не удался, остаются без вектора и ищутся только через BM25.

### Поиск

- Индекс загружается один раз за процесс (потокобезопасно): векторы — нормализованная numpy-матрица, BM25 — предрассчитанные вклады термов.
- Токенизация — по буквам/цифрам с усечением слов до 6 символов (грубый стемминг для русского).
- Слияние dense и sparse через RRF (`k=60`).
- Утратившие силу документы получают множитель `0.3`.
- Из кандидатов (`3 × k`) убираются дубли внутри одного файла (пересечение токенов > 70 %).
- Реранкер вызывается через `/rerank`; если он недоступен, возвращается порядок после RRF.

### Генерация

Системный промпт требует отвечать только по контексту, ссылаться на статьи и пункты, помечать утратившие силу документы и дополнительные соглашения (с указанием основного договора). Если контекст пуст или релевантность слишком низка — возвращается «В предоставленной базе знаний информация отсутствует». При ошибках API — до 3 попыток.

### Устойчивость `solution.py`

- Любая ошибка индексации или вопроса не мешает записать `submission.csv` со всеми `id`.
- Вопросы, не уложившиеся в бюджет времени, получают запасной ответ.
- Ответ обрезается до 10 000 символов.



# Backend API

## Общая информация

Backend реализован на Go с использованием Gin и PostgreSQL.

Локальный адрес сервера по умолчанию:

```text
http://localhost:8080
```

Все API-маршруты, кроме `/` и `/health`, имеют префикс `/api/v1`.

Формат обмена данными — JSON.

## Архитектура взаимодействия

Go Backend отвечает за:
- создание и хранение пользовательских сессий;
- создание и хранение чатов;
- сохранение сообщений пользователя и ответов AI;
- хранение источников, на основании которых сформирован ответ;
- предоставление API для frontend.

Python AI Service отвечает за:
- обработку пользовательского вопроса;
- поиск релевантных фрагментов в базе знаний;
- reranking найденных фрагментов;
- генерацию ответа с использованием LLM;
- возврат ответа и использованных источников.

Go Backend взаимодействует с Python AI Service по HTTP.

## API Endpoints

### 1. Создание сессии

`POST /api/v1/sessions`

Создаёт новую пользовательскую сессию.

Тело запроса не требуется.

Пример ответа `201 Created`:

```json
{
  "id": "c1721245-fa55-4956-98fd-71946428e3c1",
  "created_at": "2026-11-15T12:00:00Z"
}
```

Полученный `id` необходимо использовать при создании чатов.

### 2. Создание чата

`POST /api/v1/chats`

Создаёт новый чат внутри существующей сессии.

Тело запроса:

```json
{
  "session_id": "c1721245-fa55-4956-98fd-71946428e3c1",
  "title": "Договоры и претензии"
}
```

Пример ответа `201 Created`:

```json
{
  "id": 1,
  "session_id": "c1721245-fa55-4956-98fd-71946428e3c1",
  "title": "Договоры и претензии",
  "created_at": "2026-11-15T12:00:00Z",
  "updated_at": "2026-11-15T12:00:00Z"
}
```

### 3. Получение списка чатов сессии

`GET /api/v1/sessions/{session_id}/chats`

Возвращает список чатов указанной сессии.

Пример ответа `200 OK`:

```json
[
  {
    "id": 1,
    "session_id": "c1721245-fa55-4956-98fd-71946428e3c1",
    "title": "Договоры и претензии",
    "created_at": "2026-11-15T12:00:00Z",
    "updated_at": "2026-11-15T12:00:00Z"
  }
]
```

### 4. Отправка сообщения

`POST /api/v1/chats/{chat_id}/messages`

Отправляет пользовательское сообщение в чат.

Backend сохраняет сообщение пользователя, передаёт вопрос в Python AI Service, получает ответ и источники, после чего сохраняет результат в PostgreSQL.

Тело запроса:

```json
{
  "content": "Какой срок рассмотрения претензии по договору?"
}
```

Пример ответа `200 OK`:

```json
{
  "message": {
    "id": 2,
    "chat_id": 1,
    "role": "assistant",
    "content": "Претензия рассматривается в течение 10 рабочих дней.",
    "created_at": "2026-11-15T12:05:00Z"
  },
  "sources": [
    {
      "id": 1,
      "message_id": 2,
      "document_id": "contract_123.txt",
      "text": "Исполнитель рассматривает поступившую претензию..."
    }
  ]
}
```

`document_id` — идентификатор документа в базе знаний.

`text` — фрагмент документа, использованный при формировании ответа.

### 5. Получение истории сообщений

`GET /api/v1/chats/{chat_id}/messages`

Возвращает сообщения чата вместе с источниками.

Пример ответа `200 OK`:

```json
[
  {
    "message": {
      "id": 1,
      "chat_id": 1,
      "role": "user",
      "content": "Какой срок рассмотрения претензии по договору?",
      "created_at": "2026-11-15T12:05:00Z"
    },
    "sources": []
  },
  {
    "message": {
      "id": 2,
      "chat_id": 1,
      "role": "assistant",
      "content": "Претензия рассматривается в течение 10 рабочих дней.",
      "created_at": "2026-11-15T12:05:01Z"
    },
    "sources": [
      {
        "id": 1,
        "message_id": 2,
        "document_id": "contract_123.txt",
        "text": "Исполнитель рассматривает поступившую претензию..."
      }
    ]
  }
]
```

## Интеграция Go Backend с Python AI Service

Go Backend отправляет Python AI Service запрос на генерацию ответа.

### Запрос

`POST /api/v1/answer`

```json
{
  "question": "Какой срок рассмотрения претензии по договору?"
}
```

### Ожидаемый ответ

```json
{
  "status": "success",
  "answer": "Претензия рассматривается в течение 10 рабочих дней.",
  "sources": [
    {
      "document_id": "contract_123.txt",
      "text": "Исполнитель рассматривает поступившую претензию..."
    }
  ]
}
```

### Поддерживаемые статусы

| Статус | Значение |
|---|---|
| `success` | Ответ успешно сформирован |
| `insufficient_context` | Недостаточно информации в базе знаний |
| `clarification_required` | Требуется уточнение вопроса |
| `refused` | Отказ от формирования ответа |

### Требования к источникам

Каждый источник должен содержать:

- `document_id` — идентификатор исходного документа;
- `text` — точный фрагмент документа, подтверждающий ответ.

Если подтверждающих источников нет, необходимо возвращать пустой массив `sources`.

Необходимо избегать генерации неподтверждённых источниками утверждений.

## Обработка ошибок

При ошибках Backend возвращает JSON с полем `error`.

Пример:

```json
{
  "error": "chat not found"
}
```

Основные HTTP-статусы:

- `200 OK` — запрос успешно обработан;
- `201 Created` — сущность создана;
- `400 Bad Request` — некорректный запрос;
- `404 Not Found` — сущность не найдена;
- `500 Internal Server Error` — внутренняя ошибка сервера.

## Важные замечания

- Сначала необходимо создать сессию, затем чат.
- Для отправки сообщений требуется существующий `chat_id`.
- История сообщений и источники сохраняются в PostgreSQL.
- Python AI Service не должен самостоятельно сохранять историю диалогов: за это отвечает Go Backend.
- URL Python AI Service задаётся через переменную окружения `AI_SERVICE_URL`.
